RCP 机器人构型接入指南

本文说明如何新增一个机器人构型包。目标是让用户只写 controller、硬件配置和 robot integration，框架负责生成 Manifest、Observation、Action 和运行时通道。

新增机器人时，不修改 RCP 协议层、Service、ToolBus 或 App。机器人包只描述“这个机器人有什么部件、如何读取、如何执行”。本文是接入流程指南；字段是否必写、字段类型和完整配置字典看 RCP配置文件说明.md；协议对象和接口格式看 RCP使用场景及协议.md。

阅读方式

第一次接入机器人时，不建议一上来就写配置文件。配置文件只是把“已经跑通的硬件能力”登记给 RCP；如果还不知道怎么读机器人状态、怎么发控制、怎么读相机，先不用看配置字段。

当前状态应该先做什么需要查哪个文档
还不知道怎么连接机器人先看机器人 SDK、厂商文档或已有 ROS2/LCM 系统，写一个最小脚本连接硬件。暂时不用看 RCP 配置。
已经能读状态、发控制、读图像把这些能力整理成 controller 方法，或确认已有 topic/端口能提供这些数据。看本文的 controller 和 source 章节。
已经知道要暴露哪些 observation/action把它们映射成 RCP 的 component、observation、action。查 RCP使用场景及协议.md 的协议对象和 value 示例。
已经知道 controller/source 怎么写再写 robot_integration.yaml 和 server config。查 RCP配置文件说明.md 的字段是否必写和字段类型。

本文不会重复完整协议字段表，也不会重复配置文件字段字典。本文里的 YAML 只用来说明“这些能力如何接入 RCP”，不是让你逐字段照抄。字段是否必写、可选字段怎么写，以 RCP配置文件说明.md 为准。

先看结论

新增机器人不是从配置开始，而是从最小硬件闭环开始。推荐顺序如下：

  1. 先用机器人原生 SDK、串口工具、ROS2/LCM topic 或相机工具，确认硬件能连接。
  2. 写最小脚本，分别验证：读取状态、发送一个安全动作、读取一帧图像、断开连接。
  3. 把最小脚本整理成 controller 方法，或确认 topic/端口可以直接作为 source。
  4. 把 controller/source 返回值整理成 RCP 协议 value，例如 {"joint_positions": [...]}。
  5. 最后写 robot_integration.yaml 和 server config，让 RCP Runtime 自动生成 Manifest、Observation、Action。
你已经跑通的能力接入 RCP 时怎么表示通常使用
Python SDK 可以读状态/发控制整理成 controller 方法。connector: module
USB 相机可以读图像作为 camera component 的 image observation。connector: port
ROS2 topic 已经在发布状态或接收动作把 topic 映射成 observation/action。connector: ros2
LCM channel 已经在传数据用 RCP 协议 JSON 作为 payload。connector: lcm

一、推荐目录结构

目录可以先建好，但真正开始写配置前，应先完成下一节的硬件最小验证。

robots/my_robot/

  README.zh-CN.md
  setup_my_robot.sh
  rynnrcp_robot_my_robot/

    config/
      robot_integration.yaml
      my_robot_server.yaml
      my_robot_teleop_source_server.yaml

二、先跑通机器人本身

在写 RCP 配置前，先确认你能用最小代码控制机器人。这个阶段和 RCP 无关，只验证机器人本身可用。

要验证的能力最小验证方式成功标准
连接机器人用 SDK、串口、网络 API、ROS2 或 LCM 建立连接。可以连接和断开，失败时能看到明确错误。
读取状态调用 SDK 或订阅 topic 读取一次关节状态、位姿或夹爪状态。能得到稳定数值，单位和关节顺序清楚。
发送安全动作发送一个很小的关节位置变化、速度命令或预定义 home 动作。机器人按预期动作，停止和断开是安全的。
读取图像读取一帧相机图像，确认宽、高、编码。能拿到有效图像 bytes 或标准图像消息。
健康状态读取 SDK 错误、硬件连接状态或 topic 状态。能区分正常、断连、读帧失败、控制失败。

如果这些最小能力还没跑通，先不要写 robot_integration.yaml。RCP 不负责猜测你的机器人怎么连接，也不替代机器人 SDK 或底层驱动。

建议先写一个和 RCP 无关的最小验证脚本，例如：

# standalone_check.py
from my_robot_sdk import MyRobotSDK

robot = MyRobotSDK(port="/dev/ttyUSB0")
robot.connect()

# 1. 读状态：确认单位、关节顺序、数值范围
positions = robot.read_joint_positions()
print("joint_positions:", positions)

# 2. 发一个安全动作：只移动很小的幅度，确认控制链路正常
target = list(positions)
target[0] += 0.01
robot.command_joint_positions(target)

# 3. 读图像：确认宽、高、编码
image = robot.read_front_camera_jpeg()
print("image bytes:", len(image))

# 4. 安全关闭
robot.close()

这个脚本成功后，再把其中的连接、读状态、发控制、读图像、关闭逻辑整理成 controller 方法。配置文件只引用这些已经验证过的方法。

三、再决定要暴露什么

机器人本身跑通后，再把能力整理成 RCP 的 component、observation 和 action。这个阶段才需要参考协议文档。

你已经跑通的能力RCP 里通常写成例子
机械臂本体componentname: robot、type: arm
读取关节状态observationname: joint_state、type: joint_state
读取前置相机observationcomponent.name: front、name: image、type: image
发送关节位置actionname: joint_position、type: joint_position
执行 home 动作actionname: home、type: prearranged
执行自定义 move_toactionname: move_to、type: custom
判断字段放哪里：随部署机器变化的真实值写到 server config；随机器人构型固定的接入逻辑写到 robot integration；App、Agent、MCP 只看到 RCP 协议对象，不知道串口、相机编号、adapter 或内部 channel。

四、一定需要主臂吗

不一定。RCP Server 只描述“一个可观测、可控制、可采集的机器人实例”。主臂只是遥操场景里的一种控制数据来源，不是 RCP 协议要求。

数据来源是否需要单独 Server适合场景配置方式
主臂 / 示教臂通常需要主从遥操、采集示教数据给主臂也启动一个 Server，通常只开启 observations，不开启 actions/data_collection。
手柄 / 键盘 / 3D 鼠标不一定人工遥控可以做成 App 输入，App 直接调用执行端 Server 的 action。
策略模型 / 脚本不一定自动控制、调试动作推荐接入 PolicyService；临时脚本也可以直接通过 Interface 调用 run_action_chunk。
ROS2 / LCM 外部系统通常不需要主臂已有机器人系统接入 RCP在 robot integration 的 source 中配置 topic 和 payload 模式。
云端平台不需要主臂RynnBot / Agent 调用App 把云端命令映射成 RCP action。

如果你只是想让 App、Agent 或 MCP 控制一个机器人，只需要启动执行端 Server。只有当你需要从另一个设备读取状态作为控制输入时，才需要额外的控制端 Server。

五、两类配置

文件谁维护写什么
server config部署者真实 robot_id、robot_name、启用开关、能力开关、硬件连接参数。
robot integration机器人包作者Manifest 模板、components、observations、actions、source、codec。

server config 写真实值；robot integration 可以用 ${...} 引用 server config。

六、协议对象名如何生成

用户在配置里只写局部 name，框架生成完整协议对象名：

observation.<component.name>.<observation.name>
action.<component.name>.<action.name>
配置片段生成结果说明
component.name: robot
observation.name: joint_state		observation.robot.joint_state机器人关节状态。
component.name: front
observation.name: image		observation.front.image前置相机图像。
component.name: robot
action.name: joint_position		action.robot.joint_position机器人关节位置控制。
component.name: robot
action.name: move_to		action.robot.move_to自定义动作。

因此，配置里不要写完整 name，例如不要写 name: observation.robot.joint_state。只写 name: joint_state，完整协议名由框架生成。

server config 里的 components 是真实部署参数组。最容易理解的写法是让参数组名和协议 component 名一致； 如果为了硬件语义使用更明确的参数组名，例如 SO101 的 front_camera 参数组生成协议 component front，必须在 robot integration 里用 ${components.front_camera.device_id} 这种显式引用写清楚。 用户看配置时，以 integration 的 components[].name 作为最终协议 component 名。

七、哪些字段是协议字段，哪些不是

字段是否协议要求说明
manifest.robot_id是当前 RCP 实例唯一 ID，App 和 Agent 用它识别设备。
manifest.robot_name是人类可读名称。
manifest.capabilities是声明 observations、actions、health、resources、data_collection 是否支持。
component.name/type是描述机器人部件，是生成协议对象名和 Manifest 的核心字段。
component.frame/dof/parent_component/description按需填写补充构型信息。机械臂通常写 dof 和 frame；没有坐标系或自由度语义的部件不要硬写。
observation.name/type是生成协议观测对象名，并决定 value_schema。
action.name/type是生成协议动作对象名，并决定 input_schema。
role否SO101 controller 需要区分 leader/follower，所以 SO101 配置会写。其他机器人不一定需要。
port否串口机器人需要。网络机器人、ROS2、LCM 不一定需要。
ip/control_port/device_id/topic否具体硬件或通信方式的实现参数，由 controller 或 connector 决定。
判断规则：App 需要知道的是协议字段；controller 启动才需要知道的是实现参数。实现参数写在 server config 的 components 下，再由 robot integration 的 source.init 引用。

八、最小 server config 示例

这一节只展示 server config 的结构：真实 robot_id、robot_name、能力开关、integration 路径和硬件参数组。完整字段字典看 RCP配置文件说明.md。

config_type: rynnrcp_server_config
version: 1

manifest:
  robot_id: my_robot_01
  robot_name: My Robot
  capabilities:
    observations: true
    actions: true
    health: true
    resources: true
    data_collection: true

integration:
  config: package://rynnrcp_robot_my_robot/config/robot_integration.yaml

components:
  robot:
    enabled: true
  front:
    enabled: true
    device_id: 0

components 下的名字建议和 robot integration 里的 components[].name 保持一致，用户读起来最省心。除了 enabled，其他字段只写你的 controller 或 source 真正需要的内容。不要为了看起来完整而照抄别的机器人字段。

如果确实想把硬件参数组写得更具体，例如 server config 里写 components.front_camera.device_id，但协议 component 叫 front，也可以；不过必须在 robot integration 里显式引用 ${components.front_camera.device_id}，不要让用户猜哪个参数组对应哪个协议 component。

串口机械臂

components:
  robot:
    enabled: true
    port: /dev/ttyUSB0

需要区分主从角色的机械臂，例如 SO101

components:
  robot:
    enabled: true
    role: follower
    port: /dev/ttyUSB0

网络控制器

components:
  robot:
    enabled: true
    ip: 192.168.1.10
    control_port: 5000

ROS2 或 LCM 接入

components:
  robot:
    enabled: true

ROS2/LCM 的 topic、msg_type、payload_mode 通常写在 robot integration 的 source 里，因为它描述的是这个 observation/action 如何通信。

九、最小 robot integration 示例

这一节只展示“一个已经跑通的 controller 如何登记成 RCP observation/action”。下面是 Python controller 通过串口连接机械臂的例子。这里的 port 只是这个 controller 的初始化参数，不是 RCP 必填字段。

config_type: rynnrcp_robot_integration
version: 1

manifest:
  robot_id: ${manifest.robot_id}
  robot_name: ${manifest.robot_name}
  embodiment_type: single_arm
  capabilities:
    observations: ${manifest.capabilities.observations}
    actions: ${manifest.capabilities.actions}
    health: ${manifest.capabilities.health}
    resources: ${manifest.capabilities.resources}
    data_collection: ${manifest.capabilities.data_collection}
  model_refs:
    urdf: null
    mjcf: null
    calibration: null
    assets: []
  metadata: {}

components:
  - name: robot
    type: arm
    parent_component: null
    dof: 6
    frame: base
    description: Arm hardware
    enabled: ${components.robot.enabled}
    observations:
      - name: joint_state
        type: joint_state
        description: Current joint positions
        frame_rate: 60
        source:
          connector: module
          module_name: rynnrcp_robot_my_robot.controller.MyRobotController
          init:
            robot_id: ${manifest.robot_id}
            # 这里写 controller __init__ 真正需要的参数。
            # 串口机器人可以写 port；网络机器人可以写 ip/control_port。
            # 不需要的参数不要写。
            port: ${components.robot.port}
          start: start
          stop: shutdown
          method_name: get_joint_positions
        codec:
          adapter: ProtocolInputAdapter
    actions:
      - name: joint_position
        type: joint_position
        description: Target joint positions
        frame_rate: 60
        source:
          connector: module
          module_name: rynnrcp_robot_my_robot.controller.MyRobotController
          init:
            robot_id: ${manifest.robot_id}
            port: ${components.robot.port}
          start: start
          stop: shutdown
          method_name: set_joint_positions
        codec:
          adapter: ProtocolActionOutputAdapter

model_refs 在配置文件里写 server 本机可访问的模型、标定或 mesh 路径，例如 /opt/robots/my_arm/model.urdf、/opt/robots/my_arm/calibration.yaml。 当 manifest.capabilities.resources 为 true 时，RynnRCP 启动后会把这些路径注册成 Resource；get_manifest 返回的是 resource_id、format、hash 等协议字段。App 或 Agent 需要通过 Resource 接口读取文件，不直接读取 server 本地路径。 当 resources 为 false 时，这些路径只作为本地配置存在，不对外暴露。

十、source 应该怎么写

source 说明这个 observation/action 的数据到底从哪里来，或者要发到哪里去。它不是协议对象本身，而是 RCP Runtime 连接真实硬件、controller 或外部通信系统的配置。

配置层负责什么例子
协议字段对外叫什么、value 长什么样。name: joint_state、type: joint_state
source这个 value 如何读取，或者 action 如何写回真实系统。method_name: get_joint_positions、topic: /joint_states
codec把真实数据和 RCP 协议 value 互相转换。ProtocolInputAdapter、Ros2StandardInputAdapter

以 observation 为例：

observation.robot.joint_state
  - 协议名：由 component.name=robot 和 observation.name=joint_state 生成
  - 协议类型：type=joint_state
  - 数据来源：source 指向 controller.get_joint_positions()
  - 返回结果：{"joint_positions": [...]}

以 action 为例：

action.robot.joint_position
  - 协议名：由 component.name=robot 和 action.name=joint_position 生成
  - 协议类型：type=joint_position
  - 执行位置：source 指向 controller.set_joint_positions(value)
  - 输入参数：{"joint_positions": [...]}

所以，读配置时可以按这个顺序理解：

  1. name 和 type 决定 RCP 对外暴露什么。
  2. source.connector 决定通过哪种方式连接真实世界。
  3. source 里的其他字段决定具体调用哪个函数、哪个端口或哪个 topic。
  4. codec.adapter 决定如何把真实数据整理成协议 value。

常见 connector 有四种：

connector用来做什么配置重点
module调用 Python controller 方法。module_name、init、start、stop、method_name。
port调用本地硬件端口对象，例如 USB 相机。port_type、init、method_name。
ros2订阅或发布 ROS2 topic。topic、msg_type、payload_mode、qos。
lcm订阅或发布 LCM channel。topic、payload_mode: protocol_json。

module：调用 Python controller

source:
  connector: module
  module_name: rynnrcp_robot_my_robot.controller.MyRobotController
  init:
    robot_id: ${manifest.robot_id}
    port: ${components.robot.port}
  start: start
  stop: shutdown
  method_name: get_joint_positions

module 的调用规则很简单：observation 方法不接收参数，返回协议 value；action 方法接收协议 value。source.init 里的字段会作为 controller 构造参数传入。

port：调用本地硬件端口对象，例如 USB 相机

source:
  connector: port
  port_type: cameras.usb_camera.USBCamera
  init:
    name: front_camera
    device_id: ${components.front_camera.device_id}
    width: 640
    height: 360
    encoding: jpg
    fps: 30
  method_name: read

ros2：订阅或发布 ROS2 topic

source:
  connector: ros2
  topic: /joint_states
  msg_type: sensor_msgs.msg.JointState
  payload_mode: ros2_standard
  qos:
    depth: 1

LCM 当前只借用通信机制，payload 使用 UTF-8 JSON，不定义自定义 LCM 类型。

十一、用户已经知道怎么控制机器人时，该怎么写

如果你已经知道“怎么获取状态、怎么获取图像、怎么发送控制”，就按下面的方式把它们映射到 RCP。

你已有的能力配置里写成controller/数据源需要提供
读取关节状态observation + type: joint_state返回 {"joint_positions": [...]}，可选 joint_velocities。
读取相机图像observation + type: image返回图像宽、高、编码和图像 bytes；adapter 会转成协议传输格式。
读取末端位姿observation + type: ee_pose返回 position 和 orientation_quat_xyzw。
发送关节目标action + type: joint_position接收 {"joint_positions": [...]}。
回 homeaction + type: prearranged接收空对象 {}，执行预定义动作。
自定义 move_toaction + type: custom接收该 action 的 input_schema，例如 {"joint_positions": [...]}。

标准 type 只返回标准协议字段：joint_state 不要夹带 joint_names、joint_torques；imu 使用 accel、gyro、可选 orientation_quat_wxyz；joint_position action 只接收 joint_positions。机器人私有字段请放到 type: robot_state observation，或使用 type: custom action。

例子：你有一个 Python SDK

假设你的机器人 SDK 已经有这些方法：

sdk.connect()
sdk.read_joint_positions() -> list[float]
sdk.command_joint_positions(list[float]) -> None
camera.read_jpeg() -> bytes

controller 可以写成：

class MyRobotController:
    def __init__(self, robot_id: str, ip: str):
        self.robot_id = robot_id
        self.ip = ip
        self.sdk = MyRobotSDK(ip)

    def start(self) -> None:
        self.sdk.connect()

    def shutdown(self) -> None:
        self.sdk.close()

    def get_joint_positions(self) -> dict:
        return {"joint_positions": self.sdk.read_joint_positions()}

    def set_joint_positions(self, value: dict) -> dict:
        self.sdk.command_joint_positions(value["joint_positions"])
        return {"accepted": True}

    # 只有 robot_integration.yaml 配置了 health.source.method_name: get_health
    # 时才需要实现这个方法。
    def get_health(self) -> dict:
        return {"errors": [], "warnings": []}

server config 写真实 IP：

components:
  robot:
    enabled: true
    ip: 192.168.1.10

robot integration 把 IP 传给 controller，并声明 observation/action：

source:
  connector: module
  module_name: rynnrcp_robot_my_robot.controller.MyRobotController
  init:
    robot_id: ${manifest.robot_id}
    ip: ${components.robot.ip}
  start: start
  stop: shutdown
  method_name: get_joint_positions

例子：图像由你的 controller 获取

如果相机不是普通 USB 摄像头，而是机器人 SDK 自己返回图像，可以把图像也写成 module observation。

class MyRobotController:
    def get_front_image(self) -> dict:
        jpg_bytes = self.sdk.read_front_camera_jpeg()
        return {
            "width": 1280,
            "height": 720,
            "encoding": "jpg",
            "image": jpg_bytes,
        }

这里的 image 可以是 JPEG/PNG bytes；encoding 说明 bytes 的编码方式。controller 不需要手动把图像转成 base64，ProtocolImageInputAdapter 会负责协议传输格式。

components:
  - name: front
    type: camera
    parent_component: robot
    frame: front_camera
    description: Front camera
    enabled: ${components.front_camera.enabled}
    observations:
      - name: image
        type: image
        description: Front RGB image
        frame_rate: 30
        source:
          connector: module
          module_name: rynnrcp_robot_my_robot.controller.MyRobotController
          init:
            robot_id: ${manifest.robot_id}
            ip: ${components.robot.ip}
          start: start
          stop: shutdown
          method_name: get_front_image
        codec:
          adapter: ProtocolImageInputAdapter

如果相机是普通本地 USB 摄像头，则更推荐使用前面的 port 示例，不需要把相机逻辑塞进机器人 controller。

例子：你已有 ROS2 topic

如果关节状态已经通过 ROS2 /joint_states 发布，可以不写 Python controller，直接配置 source：

observations:
  - name: joint_state
    type: joint_state
    description: ROS2 joint state
    frame_rate: 60
    source:
      connector: ros2

十二、controller 应该实现什么

controller 方法直接收发协议 value，不做平台 key 映射。

source.method_name 决定 Runtime 会调用哪个方法。Observation 方法无入参，返回协议 value；Action 方法接收一个协议 value。

配置Runtime 调用函数要求
observation.source.method_name: get_joint_positionscontroller.get_joint_positions()返回 {"joint_positions": [...]}
action.source.method_name: set_joint_positionscontroller.set_joint_positions(value)接收 {"joint_positions": [...]}
health.source.method_name: get_healthcontroller.get_health()仅在配置了 health 时需要实现；返回健康 payload。
source.start: startcontroller.start()启动或连接硬件。
source.stop: shutdowncontroller.shutdown()释放硬件资源。
class MyRobotController:
    def start(self) -> None:
        ...

    def shutdown(self) -> None:
        ...

    def get_joint_positions(self) -> dict:
        return {"joint_positions": [0.0, -1.5, 1.6, 0.8, 0.0, 0.0]}

    def set_joint_positions(self, value: dict) -> dict:
        positions = value["joint_positions"]
        ...
        return {"accepted": True}

    # 只有配置了 health.source.method_name: get_health 时才需要实现。
    def get_health(self) -> dict:
        return {"errors": [], "warnings": []}

十三、custom action

prearranged 和 custom 都允许构型侧自定义 action name。区别是 prearranged 只能触发预定义动作，调用 value 必须是空对象 {}；custom 可以携带结构化参数，调用 value 必须是 object，并会原样传给 controller 方法。

普通 action 的 schema 由 type 推导；custom action 建议直接在配置里写 input_schema，这样 App 调用 list_actions 时能知道该怎么填参数。如果不写，框架会把它当作开放 object。

SO101 的 move_to 只是 custom action 的一个例子，不是协议内置的唯一 custom 名字：

- name: move_to
  type: custom
  description: Interpolate to target joint positions
  frame_rate: 1
  input_schema:
    type: object
    fields:
      joint_positions:
        type: array
        items: float
        shape: [dof]
        unit: rad
  source:
    connector: module
    module_name: rynnrcp_robot_so101.controller.SO101Controller
    init:
      robot_id: ${manifest.robot_id}
      port: ${components.robot.port}
      role: ${components.robot.role}
    start: start
    stop: shutdown
    method_name: move_to
  codec:
    adapter: ProtocolActionOutputAdapter

调用时直接传：

{
  "name": "action.robot.move_to",
  "frames": [
    {"joint_positions": [0.0, -1.5, 1.6, 0.8, 0.0, 0.0]}
  ],
  "frame_rate": 1
}

如果要定义一个全新的 custom action，例如 action.robot.pick，只需要在 robot integration 中新增 action，写清楚 input_schema，并把 source.method_name 指向自己的 controller 方法。协议层不会限制 pick、move_to、calibrate 这些名字，也不会修改传入的 frame。

如果动作没有参数，例如回 home，优先用 type: prearranged；如果动作需要自定义参数，才使用 type: custom。

先做配置展开检查，确认框架能从 server config 和 robot integration 生成正确的协议对象名。

runtime = RuntimeConfig.load("robots/my_robot/rynnrcp_robot_my_robot/config/my_robot_server.yaml")

print("observations:", [item.name for item in runner.input_specs])
print("actions:", [item.name for item in runner.output_specs])

observations: ["observation.robot.joint_state", "observation.front.image"]

再启动 server：

十五、接入检查清单

  • server config 只放真实部署值和 controller/硬件启动所需参数。
  • robot integration 只描述机器人构型和 source/codec。
  • 不要把 SO101 的 role/port 当成所有机器人必填字段。
  • 如果某个字段不是 controller 初始化或通信需要的，就不要写。
  • 不需要主臂也可以接入执行端机器人；主臂只是遥操 source 的一种。
  • 如果用户已经有 ROS2/LCM topic，就优先用 connector 配置通信，不必额外包一层 controller。
  • 启用的 component 会被运行时独立启动和管理；用户不需要手动创建 runner。
  • component、observation、action 名称都用局部 name，完整协议对象名由框架生成。
  • 需要长期运行的 RL / VLA / policy 时，优先按 RCP 策略服务接入指南.html 接入 PolicyService。
  • controller 方法收发协议 value。
  • App、Agent、MCP 不知道 channel、adapter、串口或相机编号。
  • 协议字段以 RCP使用场景及协议.md 为准；配置字段以 RCP配置文件说明.md 为准。
